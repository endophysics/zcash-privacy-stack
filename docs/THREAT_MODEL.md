# Threat Model

## Security objective

Prevent a single ordinary infrastructure role from directly observing both a wallet's network identity and the exact transaction it submits, and reduce timing and query metadata that can reconstruct that relationship.

The design does not claim protection from endpoint compromise, consensus failure, or an unconstrained global adversary controlling every relevant role.

## Actor classes

### Honest but curious

Follows the protocol but retains and analyzes every visible field and public observation.

Examples:

- relay records client IP, timing, and ciphertext size;
- gateway host records relay timing and resource use;
- P2P observer records service-originated transactions;
- light-client server records ranges and queries.

### Passive malicious

May violate logging, retention, or role-separation expectations and combine passive observations, but does not delay, inject, modify, drop, or replay traffic.

Examples:

- relay retains OHTTP ciphertext indefinitely;
- network observer correlates both sides of a relay;
- gateway host studies enclave timing;
- several passive roles share datasets.

### Active malicious

May interfere with protocol execution to improve metadata inference.

Examples:

- delay or isolate one request;
- replay a request;
- submit known probe transactions;
- flood valid or invalid inputs;
- submit public conflicts;
- manipulate host time or sealed state;
- force retries or fallback;
- eclipse the node's P2P egress.

## Role observations

| Role | Sees | Should not see |
|---|---|---|
| Relay | client IP, timing, padded ciphertext, gateway | transaction plaintext |
| Gateway host | relay source, request timing/size, release timing | client IP; plaintext when TEE enabled |
| Gateway application | plaintext transaction, admission time | client IP or stable wallet identity |
| Node private pool | verified transaction and release policy | client network identity |
| P2P peers | released transaction, service origin, release time | wallet IP |
| Read server | requested public range/object | wallet addresses or exact transaction interest in privacy mode |

## Core invariants

Before release, a privately accepted transaction must not affect any public node interface or behavior.

```text
private acceptance
  ⇒ no public lookup
  ⇒ no public inventory
  ⇒ no P2P announcement
  ⇒ no block-template eligibility
  ⇒ no public conflict or eviction effect
  ⇒ no transaction-specific public log or metric
```

A wallet must not silently fall back from private OHTTP submission to direct RPC.

A relevant note detected during synchronization must not cause an immediate distinctive transaction-specific request in the read-privacy profile.

## Batch caveat

Raw batch size is not an anonymity guarantee. Transactions already public or generated by an attacker can be subtracted. Active-adversary work must report assumptions and conservative diagnostics rather than claiming anonymity equal to total batch size.

## TEE caveat

Attestation binds claims about code and configuration to a platform. It does not by itself prove absence of side channels, current honest chain state, state continuity, or non-collusion. Those assumptions must be recorded in ADRs and tested where practical.
